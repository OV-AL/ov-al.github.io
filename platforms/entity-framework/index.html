Entity Framework

The database-backed platform: persist a bounded context’s entities and durable jobs through Entity Framework Core, with no change to your handlers.

What it is

Section titled “What it is”

The Entity Framework platform is the production tier for the storage modules. Where the in-memory tier keeps data in process, the Entity Framework tier maps a bounded context to a real database through Entity Framework Core — the same handlers, the same effects, persisted to SQL. It backs DataStore entities and makes Jobs durable, and it is documented once here for every module that runs on it.

When to reach for it

Section titled “When to reach for it”

Reach for it for any deployment that must keep data across restarts or share it across hosts — which is to say, production. Develop and test against the in-memory tier; switch to Entity Framework when you wire the real environment. The switch is registration only: no handler changes, because every tier satisfies the same effects surface.

Add it to a context

Section titled “Add it to a context”

Reference the database-backed package for the module — Oval.DataStore.EntityFramework for storage, Oval.Jobs.EntityFramework for durable jobs. You do not register a database per context: AddOval discovers the package’s contributor and wires each bounded context’s storage for you, replacing the in-memory tier. What the application supplies is the provider — you register an IEfProviderConfigurator that selects the Entity Framework Core provider (Npgsql, SQL Server, SQLite) and the connection, read from configuration.

Migrations

Section titled “Migrations”

The Entity Framework tier maps each [StoredEntity] to a table — by default the entity’s pluralized name, or the Table you set on the attribute. Generate and apply schema with the standard Entity Framework Core migration tooling; the entity-to-table mapping the platform emits participates in migrations like any other EF Core model.
