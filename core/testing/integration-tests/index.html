Behavior vs. integration

Default to behavior tests on OvalTestHost. Write an integration test only to verify what the in-memory tier cannot model: real database constraints, query translation, migrations, HTTP routing and auth. The integration hosts run your same composition root over the real tier — and deliberately expose no stubbing surface.

The boundary

Section titled “The boundary”
Behavior Integration
Entry OvalTestHost.Create<App>() OvalIntegrationHost.Create<App>(o => o.UseSqlite()) / .UsePostgres(...), OvalWebTestHost
Package Oval.Testing Oval.Testing.EntityFramework (+ .Postgres, .Web)
Tiers in-memory defaults, generated stubs, fake clock/ids the real EF provider, the real web pipeline
Speed milliseconds, no Docker, deterministic seconds; Docker for Postgres
Asserts domain behavior, effect outcomes, recorded outbound calls tier fidelity: unique/FK constraints, query filters, migrations, routing, auth, middleware
Naming *Tests.cs *IntegrationTests.cs, an /Integration/ folder, or a separate project
.Stub / .Capture available absent — a compile error, not a runtime failure

The last row is a type boundary, not a convention: the integration hosts expose no stubbing or seeding surface. If a test needs a stub, it is a behavior test; if it needs the real tier, everything it exercises is real.

Writing an integration test

Section titled “Writing an integration test”

Reference Oval.Testing.EntityFramework in the test project. OvalIntegrationHost.Create<TApp> runs the same discovered AddOval as the unit host, but the arrange callback selects a real Entity Framework provider that replaces the in-memory tier. The host creates the schema, opens a fresh scope per Run, and commits on success — so a later Run reads the earlier one’s committed writes, exactly like two dispatches in production:

Real database constraints surface as effect failures, the way production sees them — a unique index rejecting a duplicate insert is a RunFail case, exactly like any other expected failure (Running & asserting effects).

UseSqlite() needs nothing installed. For Postgres, add Oval.Testing.Postgres; the test owns its database (a Testcontainers instance works well) and hands the host its connection string:

For endpoint tests — routing, auth, middleware, response envelopes — use OvalWebTestHost from Oval.Testing.Web; it composes the same UseDatabase(db => db.UseSqlite()) surface when the endpoint test needs a real database behind it.

The provider-match rule

Section titled “The provider-match rule”

The integration host runs your app’s real AddOval, so every referenced platform’s seams come along. If the app references one database platform but the test selects another — say the app references the Postgres platform for its native bulk-write and search paths, and the test calls .UseSqlite() — those provider-specific seams execute against the wrong database and fail.

The rule: .UseSqlite() is for single-provider apps. When your app references a specific database platform, test that provider’s paths with .UsePostgres(...) against the real thing. Splitting the suites into a fast SQLite project and a Docker-backed Postgres project (linking any shared domain files) keeps both honest.

Proving the tiers agree

Section titled “Proving the tiers agree”

When the same domain logic must hold over the in-memory tier and the real one, write the test bodies once: an abstract scenario class holds the [Test] methods and a small adapter surface, and a sealed [InheritsTests] subclass per project supplies the harness.

The two subclasses live in two projects because they must: a compilation that references an EF package has no in-memory tier left to test — its contributor replaced it, which is the provider-match rule again. Link the scenario file into the integration project (<Compile Include="..." Link="..." />) so the bodies stay literally identical.
