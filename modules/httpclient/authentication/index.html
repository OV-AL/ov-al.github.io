Authentication

A client carries at most one auth attribute; the credential comes from configuration, a per-tenant store, or an OAuth connection — never from your code.

What it does

Section titled “What it does”

A typed client authenticates with a single attribute. [BearerAuth] reads a Secret<string> from the client’s config section and attaches it as a bearer token; [BasicAuth] reads a username/password pair; [TenantBearerAuth] / [TenantBasicAuth] / [TenantHeaderAuth] read the credential per tenant from the TenantSecrets store (a bearer, a basic pair, or an arbitrary header); [OAuthBacked<T>] attaches a per-user OAuth token. The credential is revealed only inside the generated handler — it never appears in your code or logs.

Bearer and basic

Section titled “Bearer and basic”

Point the attribute at the secret property on the config section:

A client may declare only one auth attribute — mixing [BearerAuth], [BasicAuth], [TenantBearerAuth], [TenantBasicAuth], [TenantHeaderAuth], or [OAuthBacked<T>] is a build error. The secret property must be settable so the configuration binder can populate it.

Per-tenant tokens

Section titled “Per-tenant tokens”

When the same client serves many tenants — a Slack app in many workspaces, an API called on behalf of each customer — a single configured token is not enough. Mark the client [TenantBearerAuth("namespace", "name")] and each request carries the ambient tenant’s bearer, resolved at send time from the TenantSecrets store keyed by (namespace, name):

The token is resolved fresh for the tenant in scope on every request — the handler is shared across tenants, so one tenant’s token never leaks into another’s call. When there is no tenant in scope (a single-tenant deployment, local dev), the optional Fallback names a Secret<string> on the config section to use instead; without a fallback the client is strictly fail-closed and the provider answers 401. Register the generated Add{Client}TenantAuth() alongside the base Add{Client}(), and write each tenant’s token to the store — see TenantSecrets.

Per-tenant basic credentials

Section titled “Per-tenant basic credentials”

When a tenant’s credential is a pair — a provider whose per-tenant identity is a username + password, such as a Twilio subaccount’s account SID + auth token per tenant — use [TenantBasicAuth]. It resolves both secrets for the ambient tenant (keyed by (namespace, name) under one namespace) and attaches Authorization: Basic:

Fail-closed on the pair: unless both parts resolve (from the store, or the optional UsernameFallback / PasswordFallback config properties), no Authorization header is sent.

Per-tenant custom headers

Section titled “Per-tenant custom headers”

For any other scheme — an API key in a non-Authorization header — [TenantHeaderAuth] resolves one per-tenant secret into the header you name. ValuePrefix prepends a literal when the value needs one:

All three per-tenant attributes register through the same generated Add{Client}TenantAuth() and resolve the ambient tenant’s secret fresh on every request from the shared, pooled handler.

OAuth-backed clients

Section titled “OAuth-backed clients”

To call an API on a user’s behalf with an OAuth access token, mark the client [OAuthBacked<TProvider>] instead of a static credential — the token is attached and refreshed automatically. See OAuth for the provider declaration and connection flow.
